# Security Phase 2 and Phase 3 automation — 10 November 2026

The user confirmed BANTAY/MuniAlert as the project for continuing the security phases. This work preserves Vue 3/Capacitor and Laravel 12/Sanctum/MySQL. Existing Phase 1 and accessibility work remains in place. Implementation, local verification, deployment and municipal acceptance are separate states.

## Identity protections implemented

Administrators receive no administrator cookie/token or private account response after the password/provider step alone. Password, Google/Facebook browser callbacks and Android code exchange all use the same MFA decision. A five-minute challenge contains no API ability. Web challenges also bind to a private browser-session nonce; native challenges use a separate high-entropy proof. Enrollment needs an operator-approved 15-minute window. A stolen first-factor password cannot independently authorize initial enrollment. Secrets use Laravel encrypted casts; proofs and ten single-use recovery codes are stored as hashes, with recovery hashes additionally encrypted.

User-row then challenge-row locks serialize enrollment, recovery and factor consumption. Codes must have a newer TOTP time step than the user's last accepted code. Five failed code attempts consume a challenge and pause factor verification account-wide for five minutes, including new challenges and other devices/IPs. Successful verification resets the failure counter. Expired/consumed challenges and changed credential/role/security versions fail closed. Recovery codes are displayed once and can be replaced after fresh verification; replacing them revokes other credentials. The client renders QR codes locally and retains setup/recovery values only in memory.

Every protected API request checks active status and the credential's security version. Existing citizen version-zero sessions remain usable; old password-only administrator credentials fail and must sign in again. Administrative writes require a password (when configured) plus an authenticator/recovery code verified on the current session/token within five minutes. The client preserves the pending form, opens a verification dialog and retries the rejected request once. A cancelled verification does not save the pending action.

Password/email changes rotate security versions and revoke other credentials. Suspension, restoration, role changes and approved MFA recovery use an operator-only Artisan command with confirmation; the last active administrator cannot be suspended/demoted. These commands were tested with synthetic accounts; this task does not select real accounts for operator approval or change their roles/passwords.

## Recovery and private mail

Account recovery requires `SECURITY_RECOVERY_ENABLED=true`, a trusted `SECURITY_FRONTEND_URL`, a real configured mail transport, and the account's separately verified `local_email_verified_at`. A provider's email assertion is distinct from local email verification. Unknown, suspended, unverified and provider-only accounts receive the same generic recovery-request response. IP and per-recipient bounds apply. The email contains a 30-minute single-use proof in a URL fragment, which the client immediately removes; it is never stored in localStorage or forwarded in a request URL.

The challenge and an ID-only `security-mail` database job are inserted in one transaction on the application database. The proof stays encrypted in the private challenge row; raw proofs are not queue payloads. Jobs recheck active status, credential state, expiry and consumption before delivery. Real deployments reject log/array/fallback transports for security mail. Provider exceptions are replaced with a generic retry error so message bodies/tokens cannot enter ordinary logs. Delivery is at least once across an SMTP acknowledgement/crash boundary, not exactly once.

`hazard:work-security-mail` uses a database overlap lock and bounded three-job/30-second between-job limits, fitting the existing hPanel scheduler without a persistent daemon. SMTP timeout is bounded. A password reset revokes credentials and pending challenges, requires a new login and retains administrator MFA. Lost-factor recovery still requires saved codes or independently approved operator intervention. Real municipal enrollment/recovery policy and actual delivery remain acceptance prerequisites.

## Browser and upload protections

Production web and Android builds include a CSP meta policy. The web build also emits matching Apache/LiteSpeed `.htaccess` and a policy manifest used by Laravel's HTML response header. Scripts are restricted to self without inline script permission, `unsafe-eval` or remote script wildcards. Framing denial is in HTTP headers. MapLibre's worker/assets, blob photos, Firebase endpoints and configured HTTPS API/map origins are explicitly allowed. Extra custom provider origins must be exact HTTPS origins. Inline styles remain necessary for Vue/MapLibre layout and are permitted; inline scripts are blocked. Development HMR uses its existing development configuration. Actual Hostinger/static-file headers still need verification.

`SECURITY_SCAN_UPLOADS=true` selects a bounded ClamAV INSTREAM adapter for original bytes and the re-encoded WebP, before private evidence is saved. Infected files are rejected; scanner errors/timeouts reject with 503. Rejected malware samples are best-effort quarantined outside the public root, with no photo/report row, private visibility and a shared-lock cap of 100 files (at most 100 MB). Scheduled cleanup removes samples older than one day. Normal image decoding, dimensions and count/size restrictions remain in force. No ClamAV executable/service was available locally, so real signatures, daemon/network behavior and hosting support are unaccepted. Scanning remains disabled until that service is configured; Phase 2 deployment checks report it as unready.

Security events contain an event name, private user ID when applicable, timestamp and keyed source-IP hash. They never accept arbitrary context/payloads. Authentication, MFA, recovery, operator changes, CMS/report administration and upload outcomes are recorded. Cleanup is bounded to 1,000 expired rows per daily batch; event retention defaults to 30 days and is configurable from one to 90. Incident/evidence retention is a separate municipal policy, not established by security-log cleanup.

## Phase 3 automation implemented

The full gate now includes Larastan/PHPStan level 3 across application code (without an error baseline), strict Vue/TypeScript checking, CSP regression checks and checksum-pinned Gitleaks 8.30.1. The scanner exports intended tracked/untracked source to a private temporary directory and never reads ignored environment files, databases, uploads, caches or test traces. It scans current source, not Git history. A negative fixture verifies credential detection, full redaction and narrow exceptions. Reviewed exceptions cover only historical PHP/TS/Vue filename-to-SHA-256 evidence entries in five named files. An empty frontend API setting was separated from the next line to eliminate a cross-line false positive; no secret-value exemption was added.

GitHub Actions are pinned to resolved full commit IDs. CI definitions are local source until an authorized push and an exact-SHA GitHub run. Protected branches/release approvals, private-repository plan support, deployment secrets, staging scans, backup restoration, alerts, real cloud/Android and municipal/workload acceptance remain open. CodeQL was not enabled without confirming private-repository availability/licensing.
